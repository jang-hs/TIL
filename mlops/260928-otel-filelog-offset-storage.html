# 로그 수집기를 재시작하면 로그가 비는 이유 - filelog receiver의 오프셋과 storage

노드의 컨테이너 로그를 OpenTelemetry Collector의 filelog receiver로 모으는 구성은 흔합니다. 설정값을 하나 바꿔 데몬셋을 롤링하면, 그 몇십 초 동안 노드에 쌓인 로그가 백엔드에 영영 나타나지 않습니다. 반대로 유실을 막겠다고 start_at: beginning으로 바꾸면 재시작할 때마다 같은 로그가 다시 들어옵니다.

두 증상의 원인은 같습니다. receiver가 "어디까지 읽었는가"를 어디에 두느냐입니다. 이 글에서는 오프셋이 기본적으로 어디에 저장되는지, 파일을 무엇으로 식별하는지, 그리고 storage를 붙인 뒤에도 남는 경계 조건을 정리합니다. 코드와 문서는 opentelemetry-collector-contrib v0.162.0 기준입니다.

# 1. 오프셋은 기본적으로 메모리에만 있다

filelog receiver는 파일마다 읽은 위치(오프셋)를 기억합니다. 이 기억을 디스크에 남기는 것은 storage 옵션이고, 기본값은 비어 있습니다.

If no storage extension is used, the receiver will manage offsets in memory only.

프로세스가 내려가면 오프셋도 사라집니다. 새로 뜬 프로세스는 처음 보는 파일을 start_at에 따라 읽습니다.

start_at (default: end) - At startup, where to start reading logs from the file. Options are beginning or end.

그래서 재시작 결과는 start_at 값 하나로 갈립니다.

설정 재시작 직후 동작 결과
storage 없음, start_at: end 모든 파일을 끝에서부터 읽음 재시작 동안 쓰인 줄이 유실
storage 없음, start_at: beginning 모든 파일을 처음부터 읽음 이미 보낸 줄까지 중복
storage 있음 저장된 오프셋에서 이어 읽음 유실·중복 없이 이어짐

start_at은 "유실과 중복 중 무엇을 감수할지" 고르는 옵션일 뿐입니다. 둘 다 피하려면 오프셋을 프로세스 밖에 두어야 합니다.

데몬셋에서 이 문제가 특히 자주 드러나는 이유도 있습니다. Helm 차트는 대개 설정 ConfigMap의 해시를 파드 어노테이션(checksum/config 등)에 넣습니다. 그러면 설정을 고칠 때마다 모든 노드의 수집기가 재시작됩니다. 설정 변경이 곧 로그 공백이 되는 구조입니다.

# 2. 파일은 경로가 아니라 내용으로 식별한다

오프셋을 저장하려면 "이 파일이 아까 그 파일인가"부터 판정해야 합니다. filelog는 경로를 키로 쓰지 않습니다. 파일 앞부분 바이트로 만든 핑거프린트가 기본 키입니다.

A fingerprint is the first N bytes of the file, with the default for N being 1000.

기본값은 1KiB(1024)가 아니라 1000바이트입니다. 내용 기반 식별이라 로테이션으로 이름이 바뀌어도 같은 파일로 인식하고, 그 덕분에 이어 읽을 수 있습니다. v0.162.0 README는 inode도 함께 본다고 설명합니다.

The receiver tracks files by their internal identity (inode) and content fingerprint

이 방식에서 생기는 경계가 세 가지 있습니다.

  • 앞부분이 같은 파일은 같은 파일로 취급됩니다. 고정된 헤더로 시작하는 로그 파일이 여럿이면 서로 오프셋을 공유하는 것처럼 동작할 수 있습니다. 헤더가 길다면 fingerprint_size를 늘려야 합니다.
  • fingerprint_size를 줄이면 재수집이 일어납니다. README에 명시된 동작입니다.

    Decreasing this value will trigger re-ingestion of files larger than the new fingerprint size.

  • copytruncate 로테이션은 기본적으로 새 내용을 늦게 읽습니다. on_truncate 기본값 ignore는 원래 오프셋을 유지하므로, 잘린 파일이 그 오프셋보다 커질 때까지 아무것도 읽지 않습니다. 필요하면 read_new나 read_whole_file로 바꿉니다.

# 3. storage 붙이기 - 데몬셋에서는 hostPath가 답이다

오프셋을 디스크에 남기려면 file_storage 확장을 정의하고 receiver의 storage에서 참조합니다.

extensions:
  file_storage:
    directory: /var/lib/otelcol/file_storage
    create_directory: true      # 기본값 false - 디렉터리가 없으면 시작 실패

receivers:
  filelog:
    include: [/var/log/pods/*/*/*.log]
    start_at: end
    storage: file_storage       # 위 확장의 ID

exporters:
  otlp:
    endpoint: gateway:4317

service:
  extensions: [file_storage]    # 정의만 하고 여기 빠뜨리면 동작하지 않는다
  pipelines:
    logs:
      receivers: [filelog]
      exporters: [otlp]

file_storage의 directory는 기본적으로 미리 존재해야 합니다. create_directory가 꺼져 있으면 디렉터리가 이미 있어야 하고, 없으면 설정 검증 단계에서 directory must exist 오류로 멈춥니다. 확장은 컴포넌트 타입과 이름으로 파일을 하나씩 만듭니다. 그래서 같은 디렉터리를 receiver 여러 개가 함께 써도 서로 섞이지 않습니다.

남은 질문은 이 디렉터리를 어디에 마운트하느냐입니다.

볼륨 파드 교체 후 판단
컨테이너 파일시스템 사라짐 의미 없음
emptyDir 파드가 노드에서 제거되면 삭제 롤링 재시작에서 사라지므로 의미 없음
PVC 유지 데몬셋은 파드별 PVC를 만들 수 없음
hostPath 노드에 남음 데몬셋에서 유일하게 맞는 선택

데몬셋 파드는 노드에 고정되고, 오프셋도 그 노드의 로그 파일을 가리킵니다. 노드 디스크에 남기는 것이 의미상으로도 맞습니다.

# 데몬셋 파드 스펙 일부
spec:
  containers:
    - name: otel-agent
      volumeMounts:
        - name: varlogpods
          mountPath: /var/log/pods
          readOnly: true
        - name: file-storage
          mountPath: /var/lib/otelcol/file_storage
  volumes:
    - name: varlogpods
      hostPath:
        path: /var/log/pods
    - name: file-storage
      hostPath:
        path: /var/lib/otelcol/agent      # 같은 노드의 다른 수집기와 겹치지 않게 이름을 구분
        type: DirectoryOrCreate

여기서 권한 문제가 하나 생깁니다. DirectoryOrCreate로 kubelet이 만든 디렉터리는 root 소유입니다. 수집기 이미지는 보통 비root 사용자로 실행되므로 이 디렉터리에 쓰지 못하고 permission denied로 시작에 실패합니다. 공식 Helm 차트의 storeCheckpoints 프리셋도 같은 문제를 root 실행으로 풉니다.

Enabling this writes checkpoints in /var/lib/otelcol/ host directory. Note this changes collector's user to root

root가 부담스럽다면 initContainer로 디렉터리 소유자를 바꾸는 방법도 있습니다. 어느 쪽이든 로그 경로 마운트는 readOnly로 두어야 합니다. 그래야 쓰기 가능한 표면이 오프셋 디렉터리 하나로 줄어듭니다. SELinux를 강제하는 노드 OS에서는 hostPath 쓰기가 별도로 막힐 수 있으니 배포 후 로그에서 권한 오류를 꼭 확인해야 합니다.

# 4. start_at은 첫 폴링에만 적용된다

storage를 붙이면 start_at은 어떻게 될까요. 저장된 오프셋이 있으면 시작 시점에 다음 로그를 남기고 start_at을 무시합니다.

Resuming from previously known offset(s). 'start_at' setting is not applicable.

이 분기에서 코드는 "처음부터 읽기" 플래그를 켭니다. 즉 저장 상태를 복원한 뒤에는 처음 보는 파일을 모두 처음부터 읽습니다. 수집기가 꺼져 있는 동안 새로 생긴 파일도 빠짐없이 읽기 위한 동작입니다.

저장 상태가 없는 첫 기동이라도 start_at: end는 첫 폴링에만 적용됩니다. poll() 끝에서 같은 플래그를 켜기 때문입니다.

// pkg/stanza/fileconsumer/file.go (v0.162.0), poll() 마지막 부분
// Any new files that appear should be consumed entirely
m.readerFactory.FromBeginning = true

이 동작에서 두 가지 결론이 나옵니다.

  • start_at: end는 "새 파일은 끝부터"라는 뜻이 아닙니다. 기동 시점에 이미 있던 파일만 끝부터 읽고, 그 뒤에 나타난 파일은 처음부터 읽습니다.
  • 수집기가 오래 꺼져 있다가 저장 상태를 복원하면 그동안 생긴 파일을 처음부터 전부 읽습니다. 복구 직후 유입량이 크게 튀는 것은 정상 동작입니다. 백엔드가 이를 감당할 수 있는지 미리 따져 둬야 합니다.

# 5. 오프셋 기억에도 수명이 있다

storage를 붙였다고 모든 파일의 오프셋을 영원히 기억하지는 않습니다. receiver는 읽기를 마친 파일의 메타데이터를 세대별로 보관합니다. 폴링이 한 번 끝날 때마다 한 세대씩 밀려나고, 기본 설정(polls_to_archive 0)에서는 3세대가 지나면 버립니다.

By default, the receiver will purge the record of readers that have existed for 3 generations.

기본 poll_interval이 200ms이므로, 연속 3번의 폴링에서 매칭되지 않은 파일은 기억에서 빠집니다. 그 파일이 나중에 다시 매칭되면 receiver는 처음 보는 파일로 보고 처음부터 읽습니다. 주로 다음 경우에 이런 일이 생깁니다.

상황 왜 매칭에서 빠지는가
exclude_older_than에 걸렸던 파일이 다시 갱신됨 수정 시각이 기준보다 오래돼 제외됐다가, 쓰기가 생기면 다시 매칭
ordering_criteria.top_n으로 일부만 고름 상위 N개에 못 든 파일은 그 폴링에서 매칭 안 됨
max_batches로 폴링당 배치 수를 제한 한도에 걸리면 뒷 배치는 그 폴링에서 아예 처리되지 않음

여기서 흔한 오해 하나를 짚습니다. 매칭 파일 수가 max_concurrent_files(기본 1024)를 넘어 배치 처리되는 것만으로는 오프셋을 잊지 않습니다.

If the number of files matched in the include pattern exceeds this number, then files will be processed in batches.

코드를 보면 배치 크기는 max_concurrent_files / 2(기본 512)입니다. poll()은 한 폴링 안에서 모든 배치를 차례로 처리하고, 세대 이동(EndPoll)은 폴링이 끝날 때 한 번만 일어납니다. 그래서 매 폴링마다 모든 파일이 한 번씩 매칭되고 기억도 유지됩니다. 예외는 max_batches입니다. 한도에 걸리면 poll()이 중간에 반환되어 뒷 배치가 처리되지 않습니다.

// pkg/stanza/fileconsumer/file.go (v0.162.0), poll() 앞부분 요약
for len(matches) > m.maxBatchFiles {
    m.consume(ctx, matches[:m.maxBatchFiles])
    if m.maxBatches != 0 {
        batchesProcessed++
        if batchesProcessed >= m.maxBatches {
            return              // 세대 이동도, 오프셋 저장도 건너뜀
        }
    }
    matches = matches[m.maxBatchFiles:]
}

max_concurrent_files를 올릴 이유는 따로 있습니다. 배치가 나뉘면 한 폴링이 길어지고 파일을 열고 닫는 비용도 늘어납니다. 파일이 상한을 크게 넘는다면 상한을 올리기 전에 매칭 대상부터 줄여야 합니다.

# 5-1. 오래된 파일은 아예 매칭에서 빼기

로그 디렉터리에 더 이상 쓰이지 않는 파일이 계속 남는 워크로드가 있습니다. 프로세스가 재시작할 때마다 세션별 디렉터리를 새로 만드는 프레임워크가 대표적입니다. 이런 파일도 include에 걸리면 매 폴링마다 열어서 핑거프린트를 확인합니다. 이때 exclude_older_than(v0.99.0 추가)로 수정 시각이 오래된 파일을 처음부터 제외할 수 있습니다.

Exclude files whose modification time is older than the specified age.

receivers:
  filelog:
    include: [/tmp/app/session_*/logs/*.log]
    storage: file_storage
    exclude_older_than: 24h     # 하루 넘게 갱신이 없는 파일은 지난 세션의 잔재로 본다

기준값은 "살아 있는 파일이 갱신 없이 버틸 수 있는 최대 시간"보다 길게 잡아야 합니다. 조용한 서비스의 로그가 기준보다 오래 쓰이지 않으면 제외됐다가, 다시 쓰이는 순간 처음부터 재수집됩니다. 메인테이너가 이슈에서 직접 설명한 동작입니다.

if a file that was older than 2 hours when the collector started is modified during collector's run, it is picked up as a new file and read from the beginning.

# 6. 읽은 다음 단계에서 버려지는 경우

오프셋이 보장하는 것은 "파일에서 읽었다"까지입니다. README도 이 점을 분명히 적어 둡니다.

While the storage parameter can ensure that log files are consumed accurately, it is possible that logs are dropped while moving downstream through other components in the collector.

storage를 붙인 뒤에도 로그가 비면 파이프라인의 뒷부분을 봐야 합니다. 많이 걸리는 지점은 두 곳입니다.

배치 크기가 gRPC 수신 한도를 넘는 경우. batch 프로세서의 send_batch_size는 내보내기 시점을 정하는 트리거일 뿐, 배치 크기의 상한이 아닙니다.

send_batch_size (default = 8192): Number of spans, metric data points, or log records after which a batch will be sent regardless of the timeout. send_batch_size acts as a trigger and does not affect the size of the batch.

상한은 send_batch_max_size이고 기본값 0은 무제한입니다. 재수집처럼 한꺼번에 많이 읽히는 순간에는 배치가 수 MiB까지 커질 수 있습니다. 받는 쪽 OTLP gRPC 서버는 max_recv_msg_size_mib를 지정하지 않으면 grpc-go 기본값인 4MiB를 씁니다. 이를 넘는 요청은 다음 오류로 통째로 거부됩니다.

rpc error: code = ResourceExhausted desc = grpc: received message larger than max (5242880 vs. 4194304)

해결은 보내는 쪽에서 상한을 거는 것입니다. 받는 쪽 한도를 올리는 방법도 있지만, 상한 없는 배치는 받는 쪽 메모리 문제로 옮겨 갈 뿐입니다.

processors:
  batch:
    send_batch_size: 512
    send_batch_max_size: 1024   # 레코드 수 기준 상한. 바이트 기준이 아니므로 로그 한 줄 크기를 감안해 잡는다
    timeout: 5s

수집기가 내보내는 중에 죽는 경우. 익스포터의 전송 큐는 기본적으로 메모리에 있습니다. 오프셋은 이미 저장됐는데 큐의 데이터는 프로세스와 함께 사라질 수 있습니다. 익스포터의 sending_queue에도 같은 storage를 지정하면 큐가 디스크에 남습니다.

If the collector instance is killed while having some items in the persistent queue, on restart the items will be picked and the exporting is continued.

exporters:
  otlp:
    endpoint: gateway:4317
    sending_queue:
      storage: file_storage

# 7. 직접 확인하는 방법

설정을 바꾼 뒤에는 다음 세 가지로 동작을 검증합니다.

1) 오프셋 파일이 노드에 생겼는지. file_storage는 컴포넌트 타입과 이름으로 파일을 만듭니다.

# 노드에서
ls -l /var/lib/otelcol/agent/
# receiver_filelog_ 로 시작하는 파일이 있어야 한다

2) 재시작 후 이어 읽었는지. 저장 상태를 복원하면 info 레벨로 다음 로그가 남습니다. 이 줄이 없으면 오프셋을 못 읽은 것입니다.

kubectl logs -n <namespace> <agent-pod> | grep -E "Resuming from previously known offset|Started watching file"

Started watching file은 새 리더가 생길 때마다 찍힙니다. 재시작 직후 이 줄이 오래된 파일들에 대해 대량으로 찍힌다면 처음부터 재수집 중이라는 신호입니다.

3) 공백이 없는지. 테스트 파드에서 1초마다 증가하는 번호를 출력하게 둡니다. 그 상태로 수집기 파드를 지우고, 백엔드에서 번호가 이어지는지 봅니다. 수집기 자체 메트릭 otelcol_fileconsumer_open_files, otelcol_fileconsumer_reading_files로 열린 파일 수가 예상과 맞는지도 확인할 수 있습니다.

kubectl run seq-logger --image=busybox --restart=Never -- \
  sh -c 'i=0; while true; do echo "seq=$i"; i=$((i+1)); sleep 1; done'

# 8. 트러블슈팅 요약

증상 원인 해결
수집기 재시작 구간의 로그가 비어 있음 storage 없음 + start_at: end file_storage + hostPath
재시작마다 로그가 중복됨 storage 없음 + start_at: beginning 위와 동일
storage를 넣었는데 시작 실패 디렉터리 없음 또는 비root가 쓰기 불가 create_directory, 실행 사용자 또는 소유자 조정
롤링 후에도 오프셋이 이어지지 않음 emptyDir에 저장 hostPath로 변경
오래된 파일이 간헐적으로 통째로 재수집됨 매칭에서 3세대 이상 빠졌다가 다시 매칭 exclude_older_than을 충분히 길게, max_batches 제거
재수집 직후 ResourceExhausted 상한 없는 배치가 gRPC 4MiB 초과 send_batch_max_size 설정
복구 직후 유입량 급증 저장 상태 복원 후 새 파일을 처음부터 읽음 정상 동작, 백엔드 용량 확인

# 9. 마무리

  • filelog의 오프셋은 기본적으로 메모리에만 있습니다. start_at은 유실과 중복 중 하나를 고르는 옵션일 뿐이고, 둘 다 피하려면 file_storage가 필요합니다. 데몬셋에서는 hostPath가 유일하게 맞는 저장 위치입니다.
  • start_at은 첫 폴링에만 적용되고, 저장 상태를 복원하면 아예 무시됩니다. 이후 나타난 파일은 항상 처음부터 읽습니다.
  • 오프셋 기억은 3번의 폴링 동안만 유지됩니다. 배치 처리 자체는 문제가 아니지만, 매칭에서 빠졌다 돌아오는 파일은 다시 처음부터 읽힙니다. 읽은 뒤의 단계(배치 크기, 전송 큐)는 오프셋이 지켜 주지 않으니 따로 막아야 합니다.
